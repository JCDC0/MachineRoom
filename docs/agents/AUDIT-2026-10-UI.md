# UI audit, October 2026

Written 2026-10-20 by a one-off session on the branch `claude/dreamy-cannon-svjbvc`, from 0.1.112 (`6f21a95`). It covers the code that runs in the browser: `src/ui/**`, `src/engine/**`, `src/live/**`, `src/assistant/**`, `src/model/state.js`, `src/model/log.js`, `src/model/player.js`, `src/Stage.jsx`, `src/App.jsx`, `src/startup.js` and `src/storage.js`, and the parts of `src/model/pipeline.js` that a live page runs for hours. It was read as an attacker who can shape what reaches the page (agent output, Paperclip data, lane diffs, file names, a link the owner opens) and as a careful reviewer. The first audit (`AUDIT-2026-10.md`) covered the bridge and the pure logic. Every fix has a test that failed before the fix. File and line numbers are those of `6f21a95`.

The tests ran on Linux with Node 24.22.0, as GitHub CI does. Before: 1361 tests, 1359 passed, 2 skipped. After: 1390 tests, 1389 passed, 1 skipped. The skip that went away is `tests/pack-start.test.js`, which skips until `dist/` exists; the one left is the crash retry test, which only Windows can run.

## Severity

- **High**: a write, a paid run, a merge or a backup starts without the owner choosing it, or a key leaves the machine.
- **Medium**: the page shows another host's data as the owner's room or sends the owner's input there, a confirm step can be skipped, or the room freezes or goes blank.
- **Low**: wrong output on odd input, or slow growth in a long session, with no lasting harm.

No High finding was found. No text reaches the DOM as HTML: there is no `innerHTML`, `insertAdjacentHTML`, `dangerouslySetInnerHTML`, `href` or `title` built from text, the CSS3D cards and chips set `textContent`, and React escapes the panels. The only inline styles built from data are the meter widths (finding 4) and the scrubber marks, which are clamped.

## What this session could not check

- Anything that only Windows shows.
- A real bridge or Paperclip. Every answer came from the mock client, the fakes in the tests, the recorded demo and, for finding 1, an unresolvable host.
- The panels by eye. A headless Chromium checked the connect screen with the new notice and the demo room after 20 Replay and Live switches, at 1280 by 800. The drawer panels, the assistant and the Reviews panel were not looked at.
- The size of the leak behind finding 7. On the old build, 60 room rebuilds in headless Chromium printed no `Too many active WebGL contexts` warning, so the context leak was found by reading the code, not seen. Memory was not measured.
- The browser's EventSource behaviour behind finding 6 and N3 comes from the HTML standard (a response that is not 200 or not `text/event-stream` fails the connection with no retry), not from a real bridge answering 502.

## Needs the owner's decision

- Finding 1 sends every link that names another host to the connect screen. A bridge on another machine on the owner's network still works, after one click on Connect, and Connect saves it as before. Whether a link should be able to name another host at all is the owner's call.
- The drawer panels write through their own buttons with no confirm card: Save on a budget, Approve and Reject, Post on a comment, Hire and Save in the agent builder. Lane runs, merges and backups have cards. The card rule in ARCHITECTURE.md is written for the assistant only.
- This container had Node 22. The tests ran on Node 24.22.0 fetched with `npx node@24`, and `npm install` under Node 22 rewrote `package-lock.json`, which was put back and is not in any commit.
