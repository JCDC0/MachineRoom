# Known limits

What the room does not do, and the measurements behind each limit.

## Known limits

- Only the top-level ring is spaced from the card sizes (each card's diagonal plus a 40 unit gap), so top-level cards never overlap. A folder's children are placed in one pass: their fan is a fixed offset per sibling, so siblings in a deep fan can overlap by design (V27).
- The overview fits the hub, the root and the top-level ring from the overview angle, aimed at the hub centre (V18, V27). In the seeded replay its distance is a median of 1,754 units (largest 1,754) at 40,000 files and 1,826 (1,826) at 200,000, down from 3,633 (4,129) and 3,264 (3,647) after U24, because the room is flat and the fit no longer reaches up a sphere (`npm run scale-probe` prints the `overview distance` row). The projected ring is wider than it is tall, so the fit fills the lens width and leaves the top and bottom emptier. A name shrinks with its card, so from far away it is small. The covered row is 0 of 399 layouts at 40,000 files on 2026-10-26, and following the touched card (V15) is what makes the rows readable.
- Hermes read lines carry only a file name. When two files share it, the parser picks the one in or nearest the folder of that run's last file; with no folder yet, or a tie, the name lands at the root.
- During a tool call that names no file (most shell commands), an agent keeps its last file as its focus, so the strip and the follow camera stay on it; the owner chose this over clearing it (audit finding V3).
- Failure is read from tool status and from output text such as a test marker. A tool that fails quietly shows as ok.
- In live mode without a file list, a Hermes read shows only a file name, so a file it reads before any other agent has touched it appears at the root until its real path is seen.
- `npm run serve` serves the built viewer and the bridge on one port, so a production build needs no dev server.
- The bridge and the scripts start git by its absolute path from PATH (`gitPath()` in `server/programPath.js`), because Node on Windows runs a `git.exe` from the child's working folder first when `NoDefaultCurrentDirectoryInExePath` is not set, and a lane worktree is such a folder. They name `refs/heads/main`, never `main`, so a tag cannot stand in for the branch. A run and its children stop through `killTree()` in `server/processTree.js` (`taskkill /T /F` on Windows, the process group elsewhere). On Windows it leaves a child object that has already exited alone, because its process id may belong to another process by then; `takeRoomLock`, `takeLaneLock` and `stopLane` treat a lock as stale when its process id was created after the lock file's last change plus 2 seconds, `stopLane` passes its injected list and kill down to `stopDescendants` and `stopLeftovers`, and `descendantProcesses` and `leftoverProcesses` ignore a parent created after its child (H19, Q16b). When the harness itself has exited, or after its final `result` line, `startLane` waits 30 seconds for `close`, then stops what is left with the descendant and leftover helpers, destroys the pipes and finishes the run with the harness's own exit code, `killed: false` and a note on the record that leftovers were stopped (H20). On Linux a child that left the harness's process group and outlives it has init as its parent, so the run still ends and its pipes close, but that child keeps running unless its command line names the lane's worktree, and the note reads the same.
- The bridge allows a page only from `http://localhost:PORT` or `http://127.0.0.1:PORT` on its own port, from the Vite port 5173 only when the bridge has no `staticDir` (the dev server case), and from each exact origin in `MACHINEROOM_ORIGINS` (a comma list of `http://localhost:N` or `http://127.0.0.1:N`; other entries are skipped with a printed line). Any other Origin gets 403. A request with no Origin passes the origin gate, but `POST /api/control/reviews/LANE/merge` needs the page's Origin or a valid orchestrator token, every `/api/mcp` route and `GET /api/harnesses/KEY/models` need the page's Origin or a same-origin `Sec-Fetch-Site` header, and `POST /api/assistant` and `POST /api/decide` need the page's Origin; the assistant, decide and MCP call routes also need `confirmed: true` (U71). A lane run needs `confirmed: true`, and a merge also needs the lane's exact head sha.
- The bridge masks a key that is split across chunks of one run and stream (`createSplitMasker` in `src/briefs/audit.js`): it holds a chunk whose last line could still grow into a key, and every later frame, for at most 1 second. A key whose head was released after that second, unmasked because it was not yet a whole key, reaches the page as that head and `[key]` in the next frame. The splitter starts a new line, so text from before a gap is never joined to the chunk after it, when a chunk's `seq` is not its run's last `seq` plus one, when a chunk still has `truncated: true`, and when the socket opens again (`reset()`, Q1c).
- About half of the full test runs on this machine die inside `node.exe` 24.15.0 with 0xC0000409 (bash shows exit 127) while the test files that start a bridge run (`bridge`, `control-contract`, `bridge-reviews`). The Windows event log names Node itself at a fixed address, and a probe hit the libuv assertion `!(handle->flags & UV_HANDLE_CLOSING)` in `src\win\async.c` when a process exited right after `bridge.stop()`. The forks pool still crashes, and one worker avoids it but is 3.6 times slower (T15). A crashed run leaves its `mr-*` temp folders behind. `npm test` runs them again by itself (T15b); it is not a test failure. After the owner moved to Node 24.22.1 (2026-10-22), three full parallel runs in a row passed with no retry; the retry stays until more runs agree.
- On this machine a test that starts git or a bridge takes 1 to 4 seconds alone and up to 11 while a lane runs its own suite, so `vite.config.js` allows 20 seconds a test and a hook instead of the default 5.
- The full test run is bounded by `tests/bridge-reviews.test.js`, which took 96 seconds alone on 2026-10-25 while other lanes ran their own suites. A paired full run in one quiet window took 90.5 seconds before T1 and 51.3 after it; pairs under other lanes' load took 150 and 201 seconds before and 103 and 176 after, so the wall time follows that file and the machine's load. T1 removed the repeated git and bridge setup and left all 2151 tests running. T21 built the project review tests from a room and a project made once, read a worktree's checkout and common git folder in one command, resolved this checkout once per process, and skipped the tree read and the dead process id those tests did not need. Three full runs under other lanes' load took 104, 42 and 59 seconds before, with one lane lock failure, and 63, 78 and 42 seconds after, with 2360 tests and no failure. In the loaded runs after, the slowest test took 16.3 seconds, the review scan of the real checkout took 15.5, the project fast forward fell from 22.6 to 12.2 at its worst, and the worktree reuse test fell from 6.6 to 3.0.
- T26 ran `npm test` eight times in the opencode3 worktree on 2026-10-30 while other lanes ran their suites, before H19: six passed and two failed, on `tests/project-reviews.test.js` (a merge answered 404 where it should answer 409), `tests/orchestrators.test.js` (`branchChanges` returned null) and `tests/project-dispatch.test.js` (a 20 second time out); the cause is not known yet (T28). T28 then logged every `taskkill` and every failed `git` in ten full runs (seven passed, three failed) and 44 run-throughs of those three files under load: no `taskkill` named a `git` (none of 831 records), every failed `git` was the test's own expected exit 1 or 128 or a deleted folder, all under 909 ms, and the ten runs never failed a `git` test, so no kill hit a `git` and the cause is still not known. The only failures were in `tests/run-lane-stop.test.js`, three on `--stop` and one on the time limit: after its harness dies a run finishes by itself, so `--stop` can reach it after it is gone, and `taskkill` answers 128 with `There is no running instance of the task.`; that test now checks the run is gone instead of that the stop's output names it. The time-limit failure came from the logged probe's own 5 second kill delay, which let the grandchild's 6 second timer write.
- On a project of 40000 files `GET /api/tree` holds about 0.6 MB in the folder shape and 115 KB gzipped, and on 200000 files about 3.1 MB and 570 KB gzipped (P3d, P13); a page's first `tree` event then holds only the files added since that answer. A page older than P13 sends no `since` and gets the whole list again on the stream. The flat ring takes 0.07 ms cold and 0.08 ms warm for the 25 folders down to depth 2 at 40,000 files, and 0.06 and 0.07 ms at 200,000 (2026-10-26, after V27). The room runs the layout only when a card appears, goes, changes size or a clicked folder changes (V10, V27). In the seeded replay no top-level card overlaps another in any of the 399 layouts, and the tallest layout is 641 units at 200,000 files and 621 at 40,000, since every card lies in the hub plane except the root and a popped card (`npm run scale-probe` prints the covered and tallest rows, now over the full chain the room draws). After V11 (the folder plan runs only when the file count, the newest activity, an agent's focus or a pin changes, and resting cards and strands skip their DOM and buffer writes), AGY measured a median of 8 ms and a p95 of 36 ms at 200,000 files (9 and 40 before), and 11 and 33 at 40,000 (10 and 42), in a front window at 1280 by 800; those frame times were measured before the ring redesign.
- On a real git checkout of 200,000 files (`npm run scale-live`, P15), the first tree read takes about 3.7 seconds, the bridge holds about 190 MB, the gzip folder answer takes about 0.2 seconds, a new file reaches a page in about 1.8 seconds, and in a burst of 2000 new files over 10 seconds the bridge itself uses about 7 percent of a core, starts 3 reads, and the last file arrives 2.3 seconds after its write (S43, 2026-11-04; 4.6 seconds before it). Each `git ls-files` keeps about one core busy while it runs (0.4 seconds at 40,000 files, 3.7 at 200,000), and a burst starts a few (4 at 200,000 files, 6 at 40,000). At 40,000 files on 2026-11-04 the same burst started 3 reads and the last file arrived 2.2 seconds after its write; before the timing change it started 4 reads and the last file arrived 4.2 to 4.5 seconds after its write.
- P19 ran `npm run scale-live` once at each size on 2026-11-10, while other lanes ran, so the times are high. A lane worktree took 54 seconds to make at 40,000 files, 111 at 200,000 and 245 at 500,000 (a run with Own worktree waits that long once; reusing it took 2 to 3 seconds). At 500,000 files the first tree read took 11.6 seconds, the doctor's read 6.9 of its 10 second limit, the bridge held 422 MB after the first read, a new file reached a page in 6.1 seconds, and `GET /api/git` took about 1.9 seconds; the reviews list stayed under 1.6 seconds. A folder that is not a git checkout is walked synchronously, so the bridge blocks for 2.0 seconds at 200,000 files and 3.9 at 500,000. In Brave with the window in front, under the same load, `?replay&scale=200000` drew a frame in a median of 12 ms paused but 206 ms (p95 552) while its three agents touched about four files a second, against 36 ms at 1,000 files: each touch costs 150 to 250 ms of main thread work at 200,000 files, most of it outside what `npm run scale-probe` times. The hunts `AUDIT-2026-11-LIGHT-START.md`, `AUDIT-2026-11-LIGHT-FOLDERS.md`, `AUDIT-2026-11-LIGHT-BRIDGE.md` and `AUDIT-2026-11-LIGHT-BROWSER.md` name the causes.
- After P25 (2026-11-10) the bridge listens before its first read ends, so `GET /api/health` and the viewer answer at once and `GET /api/tree` waits for the read in flight. On the 200,000 file checkout, under other lanes' load, its used heap after the bursts was 131 MB where four kept lists held about 123 MB at rest before, and its RSS after the first read 177 MB against 233.
- P26 profiled `?replay&scale=200000` at play in the headless Chromium (2026-11-10): React is not the cost. The room's `frame` took 3.9 s of a 20 second window, and what grows is the work per drawn card, since that room opens 171 cards where the 1,000 file room opens 46: `update` and `build` in `src/engine/strings.js`, and `anchor`, `cardBaseWidth`, `cardAnchorOf` and `recompute` in `src/engine/cards.js`. In a replay the page renders `Stage` and its children on the 120 ms snapshot timer, not on each activity.
- After P36b (2026-11-11), one new file reaches a page in about 60 ms at 40,000 files and 160 ms at 200,000, where it took 365 and 1,590, because the bridge lists only the names the watcher gave. A burst of 2000 files still runs full reads; its last file arrived in 2.5 seconds at 40,000 files and 1.5 at 200,000, measured once or three times while other lanes ran.
- `cachedRunRecords` in `server/runs.js` reads unread bytes of `runs.jsonl` in chunks of at most 4 MB (`RUN_READ_CHUNK_BYTES`) and carries any cut line across chunks (P195, 2026-11-13). On a synthetic 10 MB file (10,485,930 bytes, 30,394 records), five cold reads took a median of 42.22 ms before (42.65, 42.22, 45.29, 36.54, 36.78 ms) and 43.35 ms after (43.09, 47.91, 56.28, 43.35, 39.29 ms). The cache still keeps all parsed records in memory. It hands every caller the same frozen array of frozen records and builds a new array only when new runs arrive, so a read no longer copies the whole history.
