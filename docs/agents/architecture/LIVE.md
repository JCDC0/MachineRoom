# Live mode

How a live room connects, follows its sources and takes its query parameters.

## Live mode

The first visit opens a connect screen (`src/ui/Connect.jsx`). The choice is saved in localStorage (`machineroom.settings`) with the replay speed, and the next visit reconnects by itself. A live room reads through the bridge or the simulated feed only. A saved connection with no bridge opens the connect screen. A failed live connection returns to the connect screen with a message naming the address. While a live room has had no run yet, or the link is down, a waiting overlay (`Waiting.jsx`) says why; at 900 pixels and wider it sits inside the lens at its bottom middle, and below that it stays fixed over the page. When the feed is connected, the room's file list is empty and no agent has run, one line above the card reads `This folder is empty. Open another project in Projects, or start a lane in Dispatch with C.` (`emptyRoomLine` in `src/ui/emptyRoom.js`, U124); a file, a run or an agent at work takes it away, and a replay never shows it. A close button at the right end of its header hides the card until the feed status changes, so a new connection error or a state transition shows it again. Addresses override the saved choice: `?connect` shows the screen, `?replay` opens the replay of this page's recorded session, or of the fixture or recording the address names. Ways to connect:

On the first visit to a live room whose root is not a git checkout, and whenever a page dispatches the `machineroom:projects` window event, the project picker (`src/ui/Launcher.jsx`, flag `machineroom.launcher`) covers the lower half of the page: the question `Which folder do you want to work in?`, the current folder first as `Keep working in NAME` with Enter, then the recent projects and the folders beside the current one from `projects()` with a small `git` tag on a checkout, a dim line under a row whose `git` is false (the open folder's row too) reading `Not a git repository. Run git init here.` with a Copy button that copies `git init` and reads `Copied.`, each row with its name and path, and a text box for any absolute folder path. Picking the current folder closes the card. Picking another calls `client.openProject({ path, confirmed: true })`, shows `Opening NAME...`, polls `GET /api/health` every 500 ms until it answers and `projects().current.path` is the new path (at most 30 seconds, then `The room did not come back. Run machineroom in that folder.`), and reloads the page; a 501 answer shows its sentence. Escape and Close set the flag, and `document.body` carries `has-launcher` while the card shows so the setup card waits. The ordering, the path check, the rows with their `noGit` mark and the poll are pure in `src/ui/launcher.js`.

- `/?live&bridge=http://127.0.0.1:5174` goes through the bridge. The bridge lists the agents (one per lane or session reader), sends the project file list and pushes `tree` events when files appear (a recursive watcher while the project is quiet; on the first change it closes the watcher and polls: after a read that saw new files it waits what is left of the 3 second last-file budget after that read's length, then reads again, and after a read that saw none it waits 300 milliseconds of quiet, arms the watcher and reads once more; if the watcher cannot be armed it keeps polling with the 2 second quiet and three times the last read's length; a folder-shaped `GET /api/tree` answers from the bridge's last read at any age, since it carries `version` and the stream sends what came after, and its packed body and gzip are built once per version, 29 ms for a second ask at 200,000 files against 263 for the first; the plain shape reuses a read from the last second) to each page that opened `/events` with a `tree` parameter (the control client's stream asks for none and gets none): a page's first one holds only the files added since the `version` of the list it read with `GET /api/tree` (the page sends it as `since`; the bridge keeps one full list and, for its last 4 versions, only the paths each one added and removed, and a page at the current version gets no event; every tree event carries `version`, the page asks `since` the newest it applied, a full list sets that version even when it is lower, as after a bridge restart, and a `since` the bridge no longer holds gets one full list, P72), or the whole list when it names no version the bridge still has, and each later one only the changes that page has not had (when every watcher event since the last read named a path, at most 50 of them, the bridge lists only those names with `git ls-files`, publishes a held path the list no longer answers as removed, and runs a full read after ten such partial reads or in any other case, P36b; every read leaves out what `git diff-files --name-only -z --diff-filter=D --no-ext-diff --no-textconv --relative` answers (it never writes the index), run beside the list (P68: a tenth of the time of `git ls-files --deleted`, so a full read at 40,000 files took 608 ms against 1769 ms in the same run), so a file deleted from the disk leaves without a commit, and 30 seconds after the last partial read with no watcher event the bridge runs one full read so a missed event is corrected, P51; once a read finds the folder is not a git work tree the bridge walks it with no git process until it restarts, and the quiet read is armed only by a partial read, P62): the new files, and `removed` with the paths that left the list (P43). A whole list carries `full: true`, and the page then drops the files it holds that the list leaves out and no agent touched. The page drops a removed file and a folder left with no file, never the root, and keeps a file a working agent touches or its run wrote until that run ends; an older page ignores `removed`. A page that opens `/events?tree=folders`, or asks `GET /api/tree` with `Accept: application/json; shape=folders` (a CORS-safe value, so no preflight), gets the whole list in the folder shape `{ root, shape: 'folders', folders: [[parent, name]], files: [[folder, name, ...]] }`, which names each folder once; the folder answer of `GET /api/tree` also carries `version`, and it is gzipped (async `zlib.gzip`) when the request's `Accept-Encoding` names gzip. `readFileList` in `src/live/tree.js` reads both shapes, so pages and bridges of different versions still agree. The bridge lists a git project with `git ls-files -z`, so names with non-ASCII letters arrive as they are. `GET /api/health` answers `{ ok, problems, lanes, sessions, orchestrator?, unparsed, masked }` (`lanes` and `sessions` are true when that source is on, and `orchestrator` is true when the lane source mounts the chat; `problems` names a missing project folder, a missing `dist/index.html`, the last tree read error and a session reader's last error, and `ok` is false only for the first two, since the page shows `ok: false` as a dead room). `GET /api/git` answers `{ git: false }` on a folder that is not a checkout, else `{ git: true, branch, detached, head, dirty, changes: [{ path, status }], changeCount, branches: [{ name, head, current, worktree, upstream, ahead, behind }], commits: [{ sha, parents, subject, time, refs }], truncated }`, where `changes` holds at most 200 entries read from `git status --porcelain -z` and `changeCount` the full count, with at most 200 commits from every local branch and HEAD, read at most once a second. `POST /api/git/switch` takes `{ branch, confirmed: true }`, and `POST /api/git/branch` takes `{ name, from, confirmed: true }` and makes the branch without switching to it; both need a page Origin (403 without), allow one write at a time per project (409 while one runs) and answer the new state. A switch answers 400 for an unknown branch and 409 when the checkout has uncommitted changes, status cannot be checked, an orchestrator turn runs, any lane run is open or another worktree holds the branch. No route deletes a branch, pushes, pulls, fetches or forces. Each write and each run's end sends a `git` notice (S20). `GET /api/file?path=RELATIVE` answers `{ path, size, modified, binary, truncated, text }` for a file inside the project root: it needs the page's Origin or `Sec-Fetch-Site: same-origin` (403 without), resolves the real path and answers 400 outside the root for `..`, an absolute path or a symbolic link that leads out, refuses the `.git` and `.worktrees` folders and every `.env`, `.env.*`, `.pem` or `.key` name, answers `binary: true` with no text when the first 8 KB holds a zero byte, reads at most 256 KB and sets `truncated`, and passes the text through `maskKeys`; no error names the project's path (S21). `GET /api/network` answers `{ online, checkedAt }` from a TCP connection to 1.1.1.1 on port 443 with a 3 second limit that sends nothing and closes at once, made at most once every 30 seconds however many pages ask and only while a page has asked in the last 2 minutes; the bridge sends a `network` notice when `online` changes (S21). `GET /api/mcp/servers`, `POST /api/mcp/servers`, `POST /api/mcp/servers/NAME/delete`, `GET /api/mcp/tools` and `POST /api/mcp/call` manage the MCP servers in `<runs>/mcp.json` and call their tools (H14). The server answers carry each server's env names in `envNames` and never an env value, and a save that leaves `env` out keeps the saved values. `unparsed` is `{ total, byParser, since }`: the stdout lines shaped like a tool call that no parser could read since the bridge started, counted in `accept()` with `createUnreadableCounter` so lines split over two chunks count once. `masked` is `{ total, since }`: `accept()` passes each frame through `createSplitMasker` (`src/briefs/audit.js`), which runs `maskKeys` on a frame's `chunk`, `message` and `error` and masks a key cut across two log chunks of one run and stream, before the frame goes into the history or to a page, so a key an agent prints reaches the page as `[key]`; the bridge never logs what it masked. `POST /api/decide` asks the decision model (`server/decide.js` over `decide()` in `src/decider`), with the key from `OPENROUTER_API_KEY` and the model from the body, `DECISION_MODEL` or `typesafe/jev-1.14`; without a key it answers 404, and it logs only the model, the question names, the result and the time. `GET /api/projects` answers `{ current: { path, name, git }, recent: [{ path, name, openedAt, sessions }], folders: [{ path, name, git }] }`: `recent` leaves out the current root, folders that no longer exist, and folders `shouldSkipProject` skips, missing folders leave `<runs>/projects.json` when it is read (at most once a minute), `sessions` holds at most 6 `{ id, title, endedAt }` from `<runs>/orchestrator-<hash>.json`, and `folders` lists sibling subfolders of the parent, leaving out the current folder (at most 200, by name, with `.git`). `recordProject` skips folders inside the OS temp folder (`os.tmpdir()` and `TEMP`), lane worktrees (with a `.worktrees` folder or in the room's `lanes.json`), and runs folders (`runs.jsonl`). `POST /api/projects/open` takes `{ path, confirmed: true }`, requires a page Origin, refuses a path that is not absolute, missing or not a folder with 400 and one sentence, answers 409 while an orchestrator turn runs, a lane run is open or a lane lock names a live holder (the run pid or the harness child pid, by `isHolderAlive`, which on Windows counts a process that started after the lock file as stale, P125), adds the path to `<runs>/projects.json` (at most 20, newest first, the current root added when the bridge starts), answers `{ ok: true, restarting: true, path }`, and calls `onOpenProject(path)` to restart the bridge on the new root, or answers 501 `Open another project with machineroom FOLDER.` when started without the option. `POST /api/projects/forget` takes `{ path, confirmed: true }`, requires a page Origin (403 without), refuses a path not in the list with 400, removes that entry from `projects.json`, and answers the new list (`{ current, recent, folders }`).
- `--lanes` (or `MACHINEROOM_LANES=1`) makes the bridge show lane runs live: it watches the runs folder (`MACHINEROOM_RUNS`, else `%LOCALAPPDATA%\MachineRoom\runs` on Windows or `$XDG_STATE_HOME/machineroom/runs` elsewhere) for a new `<lane>-<brief>-<stamp>.log`, reads it from its first byte as it grows, and sends `heartbeat.run.queued`, `heartbeat.run.status` running, one `heartbeat.run.log` per complete line the harness parser reads (a line with no activity sends no frame) with `stream: 'stdout'` and a growing `seq`, then `heartbeat.run.status` succeeded or failed. The held partial line is sent before the end frame; past 8 MB it is dropped and the reader skips to the next newline. Its frames go through the same path as the sessions' frames, so they are masked, kept in the history and sent on `/events`; the bridge keeps an open run's queued and running frames out of the 500-frame eviction, so a late page always gets a run's start, and unpins a run after 2 hours without a frame. It ends a run on its record in `runs.jsonl` (matched on `log`, using `exitCode` and `killed`; the file is read again only when its size or mtime changed, and only from where the last read stopped) or after 10 minutes with no growth and no record (`failed`, `error: 'no record'`), but not while the lane's `<lane>.lock` names a live run or harness process, read through `isHolderAlive` for both the run pid and the child pid, so on Windows a reused id whose process started after the lock file does not keep an orphan open (P138). A log that grows after a quiet end reopens the run with a new `running` frame and the same `runId`. Lane discovery lists the runs folder only when its change time moved since the last list or when a new log watcher event arrives, with a full list at least every 60 seconds as a safety net. A log skipped for its age when the bridge starts is adopted when its size grows, and one whose run has a record and has not grown for an hour leaves the 10 second watched set and is picked up by the next list if it grows again. `/api/agents` lists one agent per lane that has a `cli` block in the room's `lanes.json`, keyed by the lane: the lanes folder is `MACHINEROOM_LANES_DIR` when set, else `config/`, whose `lanes.json` holds only the orchestrator and whose `policy.json` routes every tier to the owner, so the owner's room lists the orchestrator and the lanes the owner makes (P49); the orchestrator's testbench sets `MACHINEROOM_LANES_DIR=docs/agents` for the fleet (`opencode` to `opencode7`, `agy` to `agy3`, `claude`, with `opencode8` to `opencode10` retired), with the parser of its harness and the `harness` and `model` of its `cli` block; the `agy`, `agy2` and `agy3` lanes run Gemini 4 Hydrogen, `agy` and `agy2` at XHigh and `agy3` at High; retired lanes are left out, with no choice made it lists the orchestrator, the subs and the session readers but no lane, each sub orchestrator is listed as `sub-<id>` with its own parser and the model the ladder names, or the first lane model of its harness when the ladder names none, and after an active lane choice only the active lanes are listed. The lane parsers are registered when the bridge starts and after a lane-only `/api/agents` answer. `GET /api/lanes` answers `{ lanes, max, chosen }` with the non-retired, non-orchestrator lanes from `lanes.json` and owner-made lanes (`readAllLanes()`) with a `cli` block, leaving out a lane on the `agy` harness unless the owner made it, each row with `custom` and `effort`, their `active` and `working` states, every lane `active: false` with `chosen: false` until saved; `POST /api/lanes/active` saves the active lane choice for the project to `<runs>/active-lanes-<hash>.json` and sends an `agents` notice; an empty list is allowed and saved as `{ lanes: [] }`, so the owner can turn off the last active lane, and `POST /api/control/runs` refuses a lane on a project with no choice with 400 (`Pick the lanes for this project first.`) and an inactive lane with 400. `GET /api/harnesses` lists each harness `run-lane` can start (`claude`, `opencode`, `agy`, `acp`, `machineroom`, `codex`, `copilot`) with `available` true when its binary is found, its models from `server/models.js` and cached live models, and its allowed effort levels. `GET /api/harnesses/KEY/models` (with `?refresh=1`, client method `harnessModels`) discovers models live for each harness, cached in `<runs>/harness-models.json` for 6 hours; for `machineroom` the list is the saved endpoint models as `NAME/MODEL` once any endpoint exists, and with no endpoint it is the built-in list only when `MACHINEROOM_API_KEY` or `OPENROUTER_API_KEY` is set, otherwise empty with `Add a Direct API key in Settings first.`; `modelAllowed(harness, id, runsFolder)` validates models against static and cached live lists, and for `machineroom` against that same endpoint or built-in list. `GET /api/endpoints` lists up to 20 saved endpoints; `POST /api/endpoints` and `POST /api/endpoints/NAME/delete` need a page Origin and `confirmed: true`; an endpoint whose provider is a preset other than Custom must use that preset's base URL; `POST /api/endpoints/quick` takes `{ provider, key, confirmed: true }` from a page, saves the key in a slot named after the provider (or the slot of that endpoint when no other endpoint names that slot, repointing it at the provider's slot otherwise), saves or updates the endpoint named after the provider with the preset base URL, fetches its model list with the key under a 10 second limit, saves up to 1000 ids, and answers `{ endpoint: { name, provider, baseUrl, keyName, models }, error? }`, keeping the endpoint when the fetch fails; the answer, the log and every error leave the key out. The bridge keeps each endpoint model's details (name, contextLength, promptPrice, completionPrice, created) in `<runs>/endpoints.json` under `modelDetails`, and answers them with the model list. `GET /api/model-pins` answers `{ pins }` from `<runs>/model-pins.json`, and `PUT /api/model-pins` takes `{ pins, confirmed: true }` with a page Origin, saves up to 200 pinned model ids, and answers `{ ok: true, pins }`. Owner-made lanes live in `<runs>/agents.json` (at most 30), beside a `removed` list that only older rooms wrote: at start the bridge moves its keys into the project's hidden lanes, prints one line and empties it (P47), and when that move cannot write it prints `Could not move the old removed lanes: REASON` and keeps starting (P57). `POST /api/lanes/create` takes `{ name, harness, model, effort, confirmed: true }`, needs a page Origin, assigns the next free key (`claude-2`, `opencode-11`), saves it, adds it to the active lanes, or makes it the project's first active lane when none is chosen yet (P63), sends an `agents` notice and returns the lane. `POST /api/lanes/KEY/update` updates `name`, `model` or `effort` with the same checks, and `POST /api/lanes/KEY/delete` deletes any lane except `orchestrator` (400): an owner-made lane leaves `agents`, a `lanes.json` lane is hidden in this project only and still runs in other projects (the page says Remove from project for it and Delete everywhere for a made lane, which also clears its hidden mark here), both leave the active lanes, and the bridge sends `agents` and `family` notices (409 while the lane runs). `readAllLanes()` returns every `lanes.json` lane plus owner-made ones, templating each made lane from the first lane with that harness; an owner-made lane can run a task or queue on the room's project, appears in `/api/agents` and in the room, and passes its effort as `--reasoning`. `GET /api/family` builds the nodes: the main orchestrator (root), each ladder sub (parent the main, children its lanes), and every eligible lane from `readAllLanes` (parent the sub whose lanes hold it, else the main), each lane with `active` from the owner's choice so a turned-off lane stays in the tree with an off dot, with labels from `<runs>/labels-<hash>.json` and defaults `Orchestrator`, `Sub orchestrator` and `Code agent`. - Late join: through the bridge, the page asks `/events?history=1` on its first connect and gets the last 500 frames the bridge kept, so a run in progress replays from there. Every stream write after a client connects (a frame, a tree event or a keepalive) checks how many bytes the response still holds; past 8 MB over the backlog it connected with the bridge destroys that response and drops it from its client sets, so its queued output is freed and a page that stays connected but drains too slowly reconnects and the reset above brings it up to date. The writes made while a client connects (the reset, the history replay and the first tree) are not checked, since the history is at most 500 frames, so the backlog they leave stays bounded (P185, P194).
