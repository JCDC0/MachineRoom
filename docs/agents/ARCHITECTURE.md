# MachineRoom architecture

Version 0.1.300. A browser viewer that shows coding agents working on one project as a 3D machine room. It follows the room's own sources live: runs started with `run-lane` (`--lanes`), task queues on a project (S8, S8b) and the owner's Claude Code and OpenCode sessions (`--sessions`, S7a and S7b). It replays a recorded run too.

MachineRoom grew out of Paperclip: it began as its viewer and took its idea of a company of agents with tasks, budgets and approvals. Paperclip was removed on 2026-10-24, and the room now reads its own sources. S6a (0.1.233) shows lane runs live from the run-lane logs. The drawer reads tasks, live runs and costs from the lane records (`server/control.js`, `server/lane-costs.js`; L1 and L2); approvals and comments are empty, and a task, comment or agent write is refused.

## What it shows

- The middle is the hub: a flat ring where each top-level agent other than the orchestrator stays at its own slot, working or not; the orchestrator floats above the hub centre.
- Each agent is a distinct wireframe shape. A working agent shows it by its status ring, its chip and a slow pulse, and a tunnel runs in one straight solid line from the agent itself to the row of the file it touches, yellow while it works, with packets running along that line from the agent to the file, with four yellow corner brackets around that card.
- Each agent has a terminal chip beside it, joined by a thin line. The chip shows the name and a status word, and opens to show the log.
- The project folders are flat folder cards in a packed sphere around the hub, joined by straight lines: each top-level folder to the hub centre, which stands for the project root and carries its name below the agent ring, and every other folder to its parent; the root card has no line. By default the plan holds folders down to depth 2, up to 300 in all, the root included; an off-path folder below the root draws at most 4 of its children as stacked cards, with up to 3 faint cards behind it for the rest. Deeper folders appear, with a short fade, while they are on an agent's path, were touched in the last 90 seconds or are pinned. A folder on a path lists at most 3 child folders, and the folder that holds the file being touched lists up to 10 items.
- Colour has one meaning each: white is activity, red is failure, yellow is active, green is finished work.
  - A read or write flashes the file row and its card white.
  - The folder and the file an agent works on right now carry a dashed yellow outline, and the strip from the agent to the file carries yellow stripes.
  - A failed tool call, including a failed test, flashes red and leaves the file red until it is written again. A failed run turns the agent and its chip red.
  - A run that ends well turns the agent, its chip and every file it wrote in that run green.
- There is no randomness. The same recording always draws the same room.

## Data flow

1. A source sends frames: the lane source from a `run-lane` log, or the sessions source from a session file. A frame is `{id, companyId, type, createdAt, payload}`.
2. `pipeline.js` turns frames into activities. `heartbeat.run.log` carries raw agent output in `payload.chunk`; the parser for that agent turns it into tool calls.
3. `state.js` applies each activity to a mutable room state. `player.js` owns the clock and calls `onActivity` for each applied activity and `onReset` after a seek.
4. `room.js` reads the state every frame and reacts to activities with short animations (pulses, flashes, folder opening). Animations run on wall time. State changes run on replay time.

## Live mode

The first visit opens a connect screen (`src/ui/Connect.jsx`). The choice is saved in localStorage (`machineroom.settings`) with the replay speed, and the next visit reconnects by itself. A failed live connection returns to the connect screen with a message naming the address. While a live room has had no run yet, or the link is down, a waiting overlay (`Waiting.jsx`) says why. Addresses override the saved choice: `?connect` shows the screen, `?replay` opens the replay. Ways to connect:

- `/?live&bridge=http://127.0.0.1:5174` goes through the bridge. The bridge lists the agents (one per lane or session reader), sends the project file list and pushes `tree` events when files appear (a recursive watcher while the project is quiet; on the first change it closes the watcher and polls, starting a read no sooner than three times the last read's length after it, until no change for 2 seconds; a folder-shaped `GET /api/tree` may reuse a read from the last second) to each page that opened `/events` with a `tree` parameter (the control client's stream asks for none and gets none): a page's first one holds only the files added since the `version` of the list it read with `GET /api/tree` (the page sends it as `since`; the bridge keeps its last 4 versions), or the whole list when it names no version the bridge still has, and each later one only the files that page has not had, since the page only adds files. A page that opens `/events?tree=folders`, or asks `GET /api/tree` with `Accept: application/json; shape=folders` (a CORS-safe value, so no preflight), gets the whole list in the folder shape `{ root, shape: 'folders', folders: [[parent, name]], files: [[folder, name, ...]] }`, which names each folder once; the folder answer of `GET /api/tree` also carries `version`, and it is gzipped (async `zlib.gzip`) when the request's `Accept-Encoding` names gzip. `readFileList` in `src/live/tree.js` reads both shapes, so pages and bridges of different versions still agree. The bridge lists a git project with `git ls-files -z`, so names with non-ASCII letters arrive as they are. `GET /api/health` answers `{ ok, lanes, sessions, orchestrator?, unparsed, masked }` (`lanes` and `sessions` are true when that source is on, and `orchestrator` is true when the lane source mounts the chat). `unparsed` is `{ total, byParser, since }`: the stdout lines shaped like a tool call that no parser could read since the bridge started, counted in `accept()` with `createUnreadableCounter` so lines split over two chunks count once. `masked` is `{ total, since }`: `accept()` passes each frame through `createSplitMasker` (`src/briefs/audit.js`), which runs `maskKeys` on a frame's `chunk`, `message` and `error` and masks a key cut across two log chunks of one run and stream, before the frame goes into the history or to a page, so a key an agent prints reaches the page as `[key]`; the bridge never logs what it masked. `POST /api/decide` asks the decision model (`server/decide.js` over `decide()` in `src/decider`), with the key from `OPENROUTER_API_KEY` and the model from the body, `DECISION_MODEL` or `typesafe/jev-1.14`; without a key it answers 404, and it logs only the model, the question names, the result and the time.
- `--lanes` (or `MACHINEROOM_LANES=1`) makes the bridge show lane runs live: it watches `%TEMP%\machineroom-runs` for a new `<lane>-<brief>-<stamp>.log`, reads it from its first byte as it grows, and sends `heartbeat.run.queued`, `heartbeat.run.status` running, one `heartbeat.run.log` per complete line the harness parser reads (a line with no activity sends no frame) with `stream: 'stdout'` and a growing `seq`, then `heartbeat.run.status` succeeded or failed. The held partial line is sent before the end frame; past 1 MB it is dropped and the reader skips to the next newline. Its frames go through the same path as the sessions' frames, so they are masked, kept in the history and sent on `/events`; the bridge keeps an open run's queued and running frames out of the 500-frame eviction, so a late page always gets a run's start. It ends a run on its record in `runs.jsonl` (matched on `log`, using `exitCode` and `killed`; the file is read again only when its size or mtime changed, and only from where the last read stopped) or after 10 minutes with no growth and no record (`failed`, `error: 'no record'`), but not while the lane's `<lane>.lock` names a live process. A log that grows after a quiet end reopens the run with a new `running` frame and the same `runId`. A log skipped for its age when the bridge starts is adopted when its size grows. `/api/agents` lists one agent per lane that has a `cli` block in `docs/agents/lanes.json`, keyed by the lane (`opencode` to `opencode10`, and `claude`), with the parser of its harness; retired lanes are left out. The lane parsers are registered when the bridge starts and after a lane-only `/api/agents` answer. `docs/agents/lanes.json` is read from this repository, not from the project root, so `--root` can name another folder. A log with a `<log name>.meta.json` beside it is a run on another project: when its `project` resolves to the room's root (ignoring case on Windows) the source shows it and keeps its paths, and when it names another worktree of the same repository as the room's root (the same `git rev-parse --git-common-dir`), the source shows it and rewrites that worktree's path to the root, so several lanes can work in their own worktrees of one project under one room (S9); when it names any other folder the source skips it. A log with no meta file is a lane worktree run, shown only when the room's root is this checkout, this repository's main checkout from `git rev-parse --git-common-dir`, or no root at all: the source rewrites that worktree's path to the project root before the page's parser sees it, so a file inside the lane lands on the same relative path in the room's tree. AGY is a lane (S6b) but retired in `lanes.json`: its `cli` block builds `agy --print PROMPT --output-format stream-json --model MODEL --dangerously-skip-permissions` in its worktree (or the project folder), its harness maps to the `process` adapter and the `agy` parser, and its log is read by `createRunLineReader('agy')`. With `--lanes` the drawer also reads the lane runs: `GET /api/control/issues` gives one task per open or recent (newest 30) run, with the log name as its id, its briefs joined by `+` (or `project`) and the title from `TASKS.md` (or the task's first 80 characters); `GET /api/control/live-runs` gives the open runs, so the Tasks tab and the callout name a working lane's brief; comments and approvals are empty, and a task or comment write answers 409. A run's queued and finished frames send `issues` and `liveRuns` notices. `POST /api/control/runs` with a `task` and no `briefs` starts a lane on the room's own project (`run-lane --project <root> --task <text>`, with `--worktree` and `--allow-dirty` when the body says so), refused by the same project checks, and a `worktree: true` run on a folder that is not a git checkout is refused with the sentence `run-lane` would print before anything starts; with `briefs` and no `tasks` it starts a brief run only when the room's root is this repository (`git rev-parse --git-common-dir`), else 400 `Briefs run in this repository. Use a task or a queue on another project.`; the Dispatch panel offers it with a lane picker that marks a running lane `running` and does not let it be picked, a task box, an Own worktree switch (on by default, which sends `worktree: true`, and a single task as a queue of one so it is committed, so the lane works in `<project folder>-mr-<lane>` beside the project, on its own branch, never on main) and an allow-uncommitted switch (off and hidden while Own worktree is on) when the health answer says `lanes: true` (L3). With `tasks` and no `briefs` and no `task` it starts a queue instead: the list of 1 to 20 tasks, each 1 to 4000 characters and none holding a line of only `---`, is written joined by a line of `---` to `<runs folder>/<lane>-queue-<stamp>.queue.txt` and run as `run-lane --project <root> --queue <file>`, with `--worktree` when the body says so, `--allow-dirty` refused and the same project checks, plus a git checkout check that refuses a plain folder with `run-lane`'s sentence before the queue file is written; the answer and the running list carry `queue: true` and the task count. The task box takes several tasks separated by a line of `---`: with one it runs as before, with more the button reads `Run N tasks in order`, the allow-uncommitted switch is off, and the confirm card says the tasks run one after another on a new branch (in its own worktree when Own worktree is on), each committed when the project's tests pass, stopping at the first failure, never on main and never pushed (S8b).
- `--lanes` also mounts the room's orchestrator (`server/orchestrator.js`, K1). `docs/agents/lanes.json` names it as the lane `orchestrator` (Claude Code on `opus`, no worktree), and `run-lane` refuses it with `The orchestrator lane runs from the room, not from run-lane.` `GET /api/orchestrator` answers `{ state, model, project, messages }` (`idle`, `working` or `paused`, the last 200 messages from the owner, the orchestrator and the room), `POST /api/orchestrator/messages` takes a confirmed owner message of 1 to 8000 characters and starts a turn (a message sent while a turn runs waits for the next one), and `POST /api/orchestrator/stop` kills the turn with `killTree` and sets `paused` until the next owner message. A turn runs the harness its `cli.harness` names, `claude` or `opencode`, in the project, with a 60 minute limit. Claude Code runs as `claude -p` with `--session-id` on the first turn and `--resume` after that, and `docs/agents/ORCHESTRATOR-AGENT.md` appended with its placeholders filled. OpenCode runs as `opencode run --format json --model MODEL --auto --title LOGNAME` with the message, and `--session ID` after the first turn, where ID is the `sessionID` the first turn's JSON lines carry and is saved in the chat file beside the Claude session id; OpenCode has no appended system prompt, so the first turn's message starts with the filled instructions and then the owner's message. The reply is the turn's last assistant text, and the record's cost and tokens come from `summarizeRun`. stdout goes to `orchestrator-chat-<stamp>.log` with a meta beside it, and the turn appends a run record to `runs.jsonl`, so the lane source shows it at the hub centre, with the lane's parser, and ends it. Stopping the bridge or pressing Stop kills a running turn with `killTree`, and the chat is saved. A chat file whose state still says `working` opens as `idle` with a `room` message that the room restarted during a turn and asks the owner to send the message again if it still matters; an owner message that was waiting behind the turn is kept in the chat file and starts a turn after the restart. A lane run that ends wakes it with a `room` message carrying the record, at most 30 room-started turns in a rolling hour; the chat and the session live in `<runs>/orchestrator-<hash>.json`, every new message or state change sends an `orchestrator` notice, and `GET /api/health` adds `orchestrator: true` while the lane source is on.
- `--sessions` (or `MACHINEROOM_SESSIONS=1`) makes the bridge follow the owner's Claude Code sessions on the room's project: it reads `<home>/.claude/projects/<slug>/<sessionId>.jsonl`, where the slug is the project folder with every character that is not a letter or digit turned into `-`, and it reads only that folder. A file that exists when the bridge starts is read from its current end, and a file that appears later from its first byte. The reader holds a partial last line, drops it past 1 MB and skips to the next newline, and keeps only lines whose `cwd` resolves to the project root or inside it. Each kept line holds just the `tool_use` and `tool_result` items of an `assistant` or `user` line, in the stream-json shape the Claude parser reads, and a line with no kept item sends nothing. A top-level prompt line starts a run as `queued` then `running` with runId `<sessionId>:<n>`; the run ends `succeeded` at a top-level `assistant` line whose `stop_reason` is `end_turn` or after 30 seconds with no growth, and a tool line with no open run opens one. When a parent `tool_result` names an `agentId`, its `toolUseResult` also names `<sessionId>/subagents/agent-<agentId>.jsonl`: the child's kept lines go into the parent's run with `parent_tool_use_id` set to the `Agent` call, so the room shows the child with its own tool calls. The reader skips a session whose id is the `sessionId` of a `*.meta.json` in the runs folder, which is how `run-lane` marks its own Claude runs (`--session-id` in the command and `sessionId` in the meta). `/api/agents` lists it as `claude-session`, and its parser is registered when the bridge starts (S7a). It follows `session_v2` rows whose `directory` is the project root and their child sessions, skips a session whose `title` names a log in the runs folder (run-lane passes the log name as the title), starts a run at a `user` row (`<sessionId>:<seq>`), sends each `tool` item of an `assistant` row once, when its `state.status` first reads `completed` or `error`, as the `tool_use` line `opencode run --format json` prints, puts a child session's tools in its root's run, and ends the run at an `idle` row with its `outcome` or after 30 seconds with no new rows. Sessions present at start are read from their newest row on. `/api/agents` lists it as `opencode-session`. `createSessionsSource` (`server/sessions-source.js`) ticks both readers once a second, one after the other, and a reader's error never stops the other.
- `/?live&simulate&speed=3` plays the recording through the live path, for testing. The badge reads `Demo`.

## Activity schema

Every activity has `time` (ms since epoch), `agent` (key), `runId` and `order`.

| type | extra fields |
| --- | --- |
| `run.queued` | none |
| `run.start` | none |
| `run.end` | `ok`, `error` |
| `tool.start` | `id`, `tool` (read, write, edit, shell, search, other), `label`, `touches` |
| `tool.end` | `id`, `ok` |
| `error` | `text` |
| `agent.spawn` | `child` (the parent key, `~` and a number from 1 within the parent's run), `name` (at most 40 characters), `label`; `agent` is the parent |
| `agent.end` | `ok`; `agent` is the child |

The OpenCode and Hermes parsers emit `agent.spawn` and then `agent.end` at the time of a `subagent` or `delegate` line, since those harnesses report a child only when it has finished, and keep the `other` tool call for the same line. The Claude parser reads Claude Code's own stream-json (S6g): `Read`, `Write`, `Edit`, `MultiEdit` and `NotebookEdit` touch `file_path` or `notebook_path`, `Glob` and `Grep` touch a folder, `LS` lists one, and `Bash` reads its command. A `Task` or `Agent` tool call starts the child as `PARENT~N`, every later line whose `parent_tool_use_id` is that call's id carries the child's key so the child has its own tool calls and strip, and that call's `tool_result` ends it, failed when `is_error` is set. The AGY parser shows a child while it works, from what a real AGY run sends (S5, run `ffd660e6` on 2026-10-24): an `invoke_subagent` tool step (`Role` is the child's name) starts it as `PARENT~N`, labelled with the `initial_prompt` its `DONE` step carries in `subagent_info`, and it ends at the first `manage_subagents` list whose output shows it in a state other than `running`, or with the parent's `run.end`. The child's own steps go to a transcript file, not to the parent's output, so the room shows the child working with its role and prompt but no strip of its own. This AGY's file tools are `read_file`, `write_file` and `edit_file` (with `Path`), beside the older names. `scenario-g` is that real run, masked; S4's rule (a second `conversation_id` in one run is a child) stays, tested by the hand-written `scenario-f`, though the real AGY never sent one. `state.js` adds a child to the roster with `parent` and `depth` (at most 3), and the parent's `run.end` ends its children still working. The engine adds a view for a child when it appears (S2d): the next spare shape at 0.6 of its parent's size beside the parked parent (`childPlace`), a short line to it, and a chip titled `PARENT > NAME`; a child that has ended stays at full opacity for 6 seconds of wall time and then fades over 1.5 seconds (`childFade`, pure, tested; under reduced motion it goes at once after the 6 seconds). The HUD lists a child under its parent, indented 16px a level, with a `subagent` tag (`.hud-agent-row.is-subagent`, `.agent-subagent`); the number keys pick top agents only.

A touch is `{path, mode, kind}`. `kind` is `file` or `dir`. `mode` is `read`, `write` or `list`. `path` is relative to the project root, and `''` is the root.

## How each agent reports tool calls

| Agent | Adapter | Signal in `payload.chunk` |
| --- | --- | --- |
| Claude Code | `claude_local` | The older `acpx.tool_call` JSON lines, where the call name carries the path ("Read C:\...", "Edit src\math.js") or the command text for Terminal; or Claude Code's own stream-json `assistant` and `user` lines, where a `tool_use` item starts a call and a `tool_result` item ends it |
| Hermes | `hermes_local` | Plain lines such as `┊ 📖 read  strings.js  1.2s`; shown after the call finishes; reads show only the file name |
| OpenCode | `opencode_local` | JSON lines `tool_use` with `part.tool` and `part.state.input` |
| agy | `process` | JSON lines `step_update`; `ACTIVE` starts a tool, `DONE` ends it |

A shell command touches files only when its text names a known file or folder. See `commands.js` and its tests.

## Conventions

- Plain words, short sentences. No em dashes. No single-line explanatory comments.
- Fonts: Jost and Space Mono, weights 400 and 500 only. Never bold.
- Colours: white, `#e5ff00` (active), `#ff2a2a` (failure), `#2aff80` (finished) on black. Spacing on an 8px base.
- Commit message: version prefix, then a sentence. Example: `0.1.1: Add the live bridge`.
- Keep large binaries and secrets out of git. Never print a key.

## Known limits

- Only the top-level shell compares pairs of cards (up to 60 passes); stacks and fans are placed in one pass, so cards in a stack or a fan overlap by design (V21).
- The overview fits only the root and the always-present cards (V18), so its distance in the seeded replay fell from a median of 13,753 units (largest 16,801) to 7,090 (7,474) at 40,000 files, and from 14,110 (17,377) to 7,196 (7,499) at 200,000, and with the packed first shell of V21, over the full chain the room draws, to 4,233 (4,725) and 3,868 (4,282) (2026-10-24, P18) (`npm run scale-probe` prints the `overview distance` row). The cards are still small there, but each name stays at 11 pixels or more on screen; the covered row was 0 of 399 layouts at 40,000 files on 2026-10-25, and following the touched card (V15) is what makes the rows readable.
- Hermes read lines carry only a file name. When two files share it, the parser picks the one in or nearest the folder of that run's last file; with no folder yet, or a tie, the name lands at the root.
- During a tool call that names no file (most shell commands), an agent keeps its last file as its focus, so the strip and the follow camera stay on it; the owner chose this over clearing it (audit finding V3).
- Failure is read from tool status and from output text such as a test marker. A tool that fails quietly shows as ok.
- In live mode without a file list, a Hermes read shows only a file name, so a file it reads before any other agent has touched it appears at the root until its real path is seen.
- `npm run serve` serves the built viewer and the bridge on one port, so a production build needs no dev server.
- The bridge and the scripts start git by its absolute path from PATH (`gitPath()` in `server/programPath.js`), because Node on Windows runs a `git.exe` from the child's working folder first when `NoDefaultCurrentDirectoryInExePath` is not set, and a lane worktree is such a folder. They name `refs/heads/main`, never `main`, so a tag cannot stand in for the branch. A run and its children stop through `killTree()` in `server/processTree.js` (`taskkill /T /F` on Windows, the process group elsewhere).
- The bridge allows a page only from `http://localhost:PORT` or `http://127.0.0.1:PORT` on its own port, from the Vite port 5173 only when the bridge has no `staticDir` (the dev server case), and from each exact origin in `MACHINEROOM_ORIGINS` (a comma list of `http://localhost:N` or `http://127.0.0.1:N`; other entries are skipped with a printed line). Any other Origin gets 403; a request with no Origin, such as a same-origin GET or `curl`, still passes. A page on an allowed origin can still use every route, so a lane run and a merge each need `confirmed: true`, and a merge also needs the lane's exact head sha.
- The bridge masks a key that is split across chunks of one run and stream (`createSplitMasker` in `src/briefs/audit.js`): it holds a chunk whose last line could still grow into a key, and every later frame, for at most 1 second. A key whose head was released after that second, unmasked because it was not yet a whole key, reaches the page as that head and `[key]` in the next frame. The splitter starts a new line, so text from before a gap is never joined to the chunk after it, when a chunk's `seq` is not its run's last `seq` plus one, when a chunk still has `truncated: true`, and when the socket opens again (`reset()`, Q1c).
- About half of the full test runs on this machine die inside `node.exe` 24.15.0 with 0xC0000409 (bash shows exit 127) while the test files that start a bridge run (`bridge`, `control-contract`, `bridge-reviews`). The Windows event log names Node itself at a fixed address, and a probe hit the libuv assertion `!(handle->flags & UV_HANDLE_CLOSING)` in `src\win\async.c` when a process exited right after `bridge.stop()`. The forks pool still crashes, and one worker avoids it but is 3.6 times slower (T15). A crashed run leaves its `mr-*` temp folders behind. `npm test` runs them again by itself (T15b); it is not a test failure. After the owner moved to Node 24.22.1 (2026-10-22), three full parallel runs in a row passed with no retry; the retry stays until more runs agree.
- On this machine a test that starts git or a bridge takes 1 to 4 seconds alone and up to 11 while a lane runs its own suite, so `vite.config.js` allows 20 seconds a test and a hook instead of the default 5.
- On a project of 40000 files `GET /api/tree` holds about 0.6 MB in the folder shape and 115 KB gzipped, and on 200000 files about 3.1 MB and 570 KB gzipped (P3d, P13); a page's first `tree` event then holds only the files added since that answer. A page older than P13 sends no `since` and gets the whole list again on the stream. The cabinet sphere takes 0.08 ms cold and 0.09 ms warm for the 25 cards down to depth 2 at 40,000 files, and 0.14 and 0.17 ms for 39 cards at 200,000 (2026-10-23, after V21). The room runs the layout only when a card appears, goes, changes size or an open path changes (V10, V21). In the seeded replay no top-level card hides more than 70 percent of another in any of the 399 layouts, and the tallest layout is 11,743 units at 200,000 files (12,819 before V21) and 5,601 at 40,000 (9,703) (`npm run scale-probe` prints the covered and tallest rows, now over the full chain the room draws). After V11 (the folder plan runs only when the file count, the newest activity, an agent's focus or a pin changes, and resting cards and strands skip their DOM and buffer writes), AGY measured a median of 8 ms and a p95 of 36 ms at 200,000 files (9 and 40 before), and 11 and 33 at 40,000 (10 and 42), in a front window at 1280 by 800; those frame times were measured before the sphere redesign.
- On a real git checkout of 200,000 files (`npm run scale-live`, P15), the first tree read takes about 3.7 seconds, the bridge holds about 190 MB, the gzip folder answer takes about 0.2 seconds, a new file reaches a page in about 1.8 seconds, and in a burst of 2000 new files over 10 seconds the bridge itself uses about 7 percent of a core and the last file arrives 1.7 seconds after its write. Each `git ls-files` keeps about one core busy while it runs (0.4 seconds at 40,000 files, 3.7 at 200,000), and a burst starts a few (4 at 200,000 files, 6 at 40,000).
