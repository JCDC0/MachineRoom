# Audit of the lane runner, the bridge and the MCP routes, for a first deployment

Written 2026-10-27 by OpenCode 6 on the branch `feat/a8-audit-the-harness`, at `007c14b` (0.1.389), for brief A8. It reads `scripts/run-lane.mjs`, `scripts/candidate.mjs`, `bin/machine-room.mjs`, `server/index.js` and the routes it mounts, `src/briefs/briefs.js`, `server/mcp.js`, `scripts/mcp-bridge.mjs`, the lane records under `%TEMP%\machineroom-runs`, and the doc lines a first-time owner follows in `README.md` and `docs/agents/ARCHITECTURE.md`. File and line numbers are those of `007c14b`. The suite at that commit has 3056 tests in 182 files. The branch was cut from `refs/heads/main` at `007c14b`.

The audit before this one is `AUDIT-2026-10-V7.md` (the ladder, the dock and the harness registry). This one does not repeat its findings. It asks what stops a first-time owner from finishing a real run: a route that writes without a confirmation, a lane that can reach the main checkout or another lane's worktree, a key or environment variable that reaches a lane, a run record written with its branch or worktree half done, two runs on one lane, a brief that can name a forbidden path, an MCP server or tool started without a confirmation, an origin or port check another site can pass, and a doc line that leads a beginner into a failure.

## Severity

- High: a normal load or a normal click shows the room wrong.
- Medium: a normal case, such as a seek, a failed tool call or a folder change, shows wrong output, or a resource grows over a session, with no lasting harm.
- Low: odd input, extra work per frame, or slow growth with no lasting harm.

Read for a first deployment, High is A1: a lane can change the owner's main checkout with no owner action, which is the lasting harm the scale names. The cases that need a hand-edited `lanes.json`, a second program or a second request are Medium or Low. A1 is the only High. A2 and A3 start a process or spend money without the owner, but the lane already has a shell and the owner chose the MCP server, so they are Medium; A5 puts a key in reach of the same lane. A6, A9 and A12 are three parts of the project-run workflow: the worktree is left half done, its branch is not in the documented field, and the summary names the wrong folder.

## What was checked and found sound

- Two runs on one lane. `takeLaneLock` creates `<runs>/<lane>.lock` with `wx`, records the pid, checks a live holder with `process.kill(pid, 0)`, and uses a takeover file for a stale lock (`scripts/lane-lock.mjs:30-68`). A project run also holds a project lock, and the worktree lock is the worktree path so two lanes in their own worktrees can run side by side. The bridge's `running` map refuses a second run from the page (`server/runs.js:532-535`). `tests/lane-lock.test.js` and `tests/run-project.test.js:374` pass. The 346 real records have one apparent 0.5 second overlap on `opencode` on 2026-10-21, which is the rounded `minutes` of two back-to-back runs, not a second start: the file's `startedAt` values are 3 minutes 42 seconds apart and the first run reports 3.7 minutes. The UI does not learn about a terminal run's lock until the child exits, so a second start from the page shows a failed run instead of the lock sentence; the lane still does not run twice.
- The `--project` refusals. `projectProblems` refuses this checkout, the main checkout, a folder that holds either, a git checkout that shares this repository's common dir, a lane worktree, the user profile, a folder that holds it, the OS temp folder, the runs folder and a dirty folder without `--allow-dirty` (`src/briefs/run.js:435-479`). `worktreePlan` refuses a worktree that is not a git checkout or belongs to another repository (`scripts/run-lane.mjs:90-103`). `tests/run-project.test.js` and `tests/run-worktree.test.js` pass.
- The origin and host checks. `isAllowedHost` accepts only `localhost`, `127.0.0.1` and `[::1]`, with or without a port; `isAllowed` accepts only the serving port, the Vite port while the bridge is not serving the built viewer, and the origins named in `MACHINEROOM_ORIGINS`. A request with a foreign Origin gets 403 before any route (`server/index.js:59-61`, `:260-264`, `:730-740`). The gap is the requests with no Origin at all, which A2 and A3 use.
- The orchestrator routes. The actor comes from the Origin (owner) or the `X-MachineRoom-Orchestrator` token (an orchestrator), not from the body; `by`, `from` and `startedBy` are checked against the actor; the sector check applies to a sub; the message, stop, ladder, autocompact, compact, model, harness, effort and session routes require `confirmed: true` (`server/orchestrators.js:402-471`, `:478-519`; `server/orchestrator.js:987-1271`). The V7 X1 fix holds at `007c14b`.
- The merge checks other than the actor. The route requires a 40-character head, a clean main checkout on `main`, a clean lane, a head that has not moved, a merge that is not a no-op, and one merge at a time; a conflict is aborted and the checkout is checked against its old head (`server/reviews.js:255-321`, `:421-461`). `tests/bridge-reviews.test.js` covers every refusal, a conflict and two merges at once, and passes. A1 is the missing actor check, not the merge itself.
- The MCP protocol. `server/mcp.js` initializes over stdio or HTTP, lists tools, calls one, uses 8 and 15 second timeouts, settles every pending request, and kills the child with `killTree`. `scripts/mcp-bridge.mjs` does the same for the `machineroom` harness, with a paged tool list and a stderr tail. `tests/mcp-server.test.js` and `tests/mr-agent-mcp.test.js` pass. A2 is the route gate, not the transport.
- The brief refusals. `briefProblems` refuses a missing brief, a repeated id, a merged brief, an owner that does not match, an existing branch, the orchestrator lane and a retired lane; `--force` skips the merged, owner and retired checks but not the branch (`src/briefs/run.js:194-241`; `scripts/run-lane.mjs:583-586`). `tests/briefs.test.js` and `tests/run-lane.test.js` pass.
- The first-owner command paths. `bin/machineroom.mjs` rewrites `machineroom [FOLDER]` to `up --root ... --open`, so the README's short path does run `up`, sets the lane and session sources, runs the doctor and prints `MachineRoom is running.` (`bin/machineroom.mjs:14-21`; `bin/machine-room.mjs:198-206`; `server/doctor.js:204-219`). `npm run serve -- up --root FOLDER` does the same through `bin/machine-room.mjs`. The `--port 0` path works because `servingPort` is updated after `listen`. `tests/serve.test.js` and `tests/machine-doctor.test.js` pass.
- The lane records. A scan of `%TEMP%\machineroom-runs\runs.jsonl` found 346 records, 0 bad JSON lines, 0 empty lane names, 0 null exit codes and 0 missing `startedAt` values. The 4 records with no brief and no project are the orchestrator's own chat turns, which is expected. The records name `branch` for brief runs and leave it empty for project and queue runs (A6 and A9).
- The candidate's worktree checks. It refuses a dirty lane, a missing lane, a lane with no worktree and a lane whose worktree is not a git repository, and it strips key-shaped names from the build and candidate environment (`scripts/candidate.mjs:76-82`, `:199-217`, `:288-292`). A10 is the port check's window.

- The lane records change while other lanes run. The scan is a point in time at `007c14b`.
