## MCP servers (H14, done 0.1.388)

The bridge keeps the Model Context Protocol servers the owner adds in `<runs>/mcp.json`, as `{ servers: [{ name, transport, command, args, env, url, enabled }] }`. A name is 1 to 40 letters, digits, dashes or underscores. A `stdio` server needs a command, and an `http` server needs a full http or https URL.

Five routes serve them: `GET /api/mcp/servers`, `POST /api/mcp/servers` (a confirmed save, which adds or replaces by name and sends an `mcp` notice), `POST /api/mcp/servers/NAME/delete` (confirmed, also an `mcp` notice), `GET /api/mcp/tools` and `POST /api/mcp/call`. A call answers `{ ok, result, problem }` and keeps the tool's own `isError` result.

`readMcpServers`, `writeMcpServers`, `upsertMcpServer` and `removeMcpServer` are the storage half. `listMcpServerTools`, `callMcpServerTool`, `listAllMcpTools` and `callMcpTool` are the client half. The client speaks MCP JSON-RPC 2.0 with `initialize` at protocol `2024-11-05`, `notifications/initialized`, `tools/list` and `tools/call`. A stdio server gets newline-delimited JSON-RPC on stdin and stdout and inherits the bridge's environment with its own `env` on top; its command must be a program Node can start directly, such as `node` or a full path to an executable. An http server gets each message as a JSON POST to its URL, keeps the `Mcp-Session-Id` header the server sends, and reads a JSON or event stream answer. A tool list gives up after 8 seconds and a tool call after 15. `listAllMcpTools` queries every enabled server, tags each tool with its server and names a server that fails in `errors`; `callMcpTool` finds a server by name and refuses one that is off.

## Where a harness is named today

After H1 and H2, adding a harness means touching these:

| Place | What it holds |
| --- | --- |
| `src/model/parsers/unreadable.js` | the list of parsers the unread-line counter knows |
| `src/engine/shapes.js` | the wireframe shape per agent key |
| `server/harnesses/<key>.js` (S7) | `createSessionsReader`, a reader of the harness's own session files (Claude Code, OpenCode and Antigravity today) |
| `server/agents-config.js` | `HARNESS_KEYS`, `HARNESS_NAMES`, `HARNESS_EFFORTS` and the Codex app fallback |
| `server/model-list.js` | the static `MODELS` list per harness (re-exported by `server/models.js`) |
| `server/harness-models.js` | per-harness live model discovery commands and output parsers |
| `src/control/modes.js` | `LISTS` and `LEGACY` permission modes per harness |
| `src/briefs/run.js`, `server/orchestrator.js` | `laneModeProblem` (OpenCode mode restriction), session-harness branches (`claude` and `opencode`) and default `effortLevelsFor` fallback |

The parser map in `src/live/source.js` reads `harnessByAdapter`. The UI lane lists read the registry and the agent list: `VALID_LANES` and `validLanes` in `src/ui/panels/briefs.js` read `docs/agents/lanes.json` and an agent list, and the project run lanes in `src/ui/panels/runs.js` read the agents `/api/agents` sends. The bridge puts each agent's parser in `/api/agents`, so `server/index.js` has no adapter map.

## The plan

One descriptor per harness, in two halves, because the browser bundle must not pull in `node:fs` or `node:sqlite`:

- `src/harnesses/<key>.js`, pure and browser-safe: `key` (the `cli.harness` value in `lanes.json`), `name`, `adapterType`, `createParser`, `command({ cli, prompt, folder, env, title, sessionId })` returning `{ file, args, cwd }`, `readLine` (a factory: it returns the line reader, because the parser keeps state across lines; used by recordings and the live lane source), `report(log)` and `usage(log)`, and an optional `shape`. AGY's adapter `process` is generic, so its descriptor sets `parserByAdapter: false` and the parser picker uses it only when an agent names `parser: agy`.
- `server/harnesses/<key>.js`, Node only and optional: `createSessionsReader` (the S7 reader interface).
- `src/harnesses/index.js` and `server/harnesses/index.js` list them, with `harnessByKey` and `harnessByAdapter`, and the agent and brief owner orders. The steps below move every place in the table onto the registry.

How a harness program is found (`resolveHarnessProgram` in `server/harness-models.js` and `isHarnessAvailable` in `server/agents-config.js`):
- First, the saved program path for that key in `<runs>/harnesses.json` (`programs[key]`, set in Settings under Harnesses).
- Second, `cli.bin` from any lane using that harness in the room's lanes file or `<runs>/agents.json`.
- Third, the harness descriptor's `defaultProgram` (`src/harnesses/<key>.js`, expanding `%VAR%` and checking an explicit file path or `PATH`, plus `.exe` and `.com` on Windows), with `resolveHarnessProgram` also checking the bare harness key on `PATH` when `defaultProgram` differs.
- Fourth, for `codex` when `codex` is not on `PATH` and no custom binary was set, the newest real `codex.exe` inside `%LOCALAPPDATA%\OpenAI\Codex\bin\HASH\codex.exe` (`codexAppProgram`, skipping symlinks and junctions). For `machineroom`, no binary is searched; availability is true when a saved endpoint exists or `MACHINEROOM_API_KEY` or `OPENROUTER_API_KEY` is non-empty.

What `ready` and `off` mean (`harnessStatus` in `server/harness-settings.js` and `src/ui/harnessesSettings.js`):
- If `<runs>/harnesses.json` lists the key in `off`, `enabled` is false and Settings shows `Off`; new lanes, new subs, harness switches and lane runs, including failover runs, are refused with `That harness is turned off in Settings.` An orchestrator or sub already using that harness keeps taking turns.
- Otherwise `Settings` shows `Ready` when the readiness check succeeds, or `Not ready` with its reason: for `machineroom`, `ready` equals `available` (reason `No key or endpoint is saved.` when false); for CLI harnesses, the resolved program (`No program was found.` if none) is run with `--version` and a 5 second timeout (`The program did not answer a version check.` on failure), and exit ok sets `ready: true` with the first stdout line (up to 80 characters) as `version`. Version checks are cached in memory per `(runsFolder, key)` while the resolved program matches and is under 10 minutes old, and `POST /api/harnesses/check` (`Check again`) clears the cache and re-runs all checks. The lane's `"retired": true` flag in `lanes.json` still turns individual built-in lanes off, while `/api/harnesses` lists the registry keys and `Settings` controls `harnesses.json`.

The generic path: the `acp` harness runs any Agent Client Protocol agent (`opencode acp`, `dsh --profile acp`, Zed's `claude-agent-acp`) and maps each `tool_call` `kind` and `locations` to touches (see `SOURCES.md`, results of 2026-10-24). With it, a new ACP agent needs only a `lanes.json` entry naming its command.

4. H4 (done, 0.1.305). The `acp` harness, tested on `opencode acp` with the probe in `scripts/acp-probe.mjs` and end to end with a fake ACP agent.
5. H5 (done, 0.1.386). The `machineroom` harness: `scripts/mr-agent.mjs` reads `MACHINEROOM_API_KEY` or `OPENROUTER_API_KEY`, calls `{url}/chat/completions` with read, write, edit, list, search and shell tools, and prints the assistant, tool result and result lines in Claude Code's stream-json shape. `isHarnessAvailable` reports it when either key is set (or an endpoint is saved), and the two OpenRouter models in `server/model-list.js` (re-exported by `server/models.js`) are its built-in models.
6. H10 (done, 0.1.386). Provider endpoints: `server/endpoints.js` keeps up to 20 endpoints in `<runs>/endpoints.json` with a provider preset, a base URL, a key slot and up to 1000 models. `GET /api/providers`, `GET /api/endpoints`, `POST /api/endpoints`, `POST /api/endpoints/NAME/delete` and `GET /api/endpoints/NAME/models` serve them, and the model list asks `BASEURL/models` with the slot key and a 10 second timeout. A `machineroom` lane may carry `cli.endpoint`, `run-lane` adds `--endpoint NAME`, and `mr-agent` reads the endpoint and its key slot instead of the environment keys. `server/models.js` lists each endpoint's models for the harness as `NAME/MODEL`, and Settings has `Direct API` below `Harnesses`.
7. H12 (done, 0.1.386). `scripts/mr-agent.mjs` also has `web_search` and `web_fetch`. Search goes through the provider saved in `<runs>/search.json`: SearXNG at the owner's address, Tavily or Brave with a key slot, or DuckDuckGo with no key. `web_fetch` takes http and https only, refuses localhost and private, loopback and link-local addresses after resolving the name, follows at most 3 redirects with the same check, stops at 1 MB and 20000 characters, and gives up after 20 seconds. The tools print `WebSearch` and `WebFetch` tool items, and the provider has `GET` and `POST /api/search-provider` with a Web search section in Settings.
8. H11 (done, 0.1.386). The `codex` and `copilot` harnesses: `codex exec` with `--json`, `--sandbox workspace-write` and model reasoning effort, and GitHub Copilot CLI with `-p`, `--allow-all-tools` and JSON or plain tool line parsing.
9. H13 (done, 0.1.388). Live model lists per harness: `server/harness-models.js` and `GET /api/harnesses/KEY/models` (with `?refresh=1`). Runs `agy models` (tab-separated id and label after the fetching header), `opencode models` (one id per line), `codex` and `copilot` from their list command if help shows one, `machineroom` from saved endpoints plus the static list, and `claude`, `hermes` and `acp` from the static list. Answers are cached in `<runs>/harness-models.json` for 6 hours. `modelAllowed(harness, id, runsFolder)` validates models across lane create, update, proposals and orchestrator routes.

10. H15 (done, 0.1.388). MCP tools for the harnesses. `scripts/mcp-bridge.mjs` reads `{ servers: [...] }` from `<runs>/mcp.json`, where the runs folder is `MACHINEROOM_RUNS_DIR`, else `runsFolder(env)` (`MACHINEROOM_RUNS`, else `%LOCALAPPDATA%\MachineRoom\runs` on Windows or `$XDG_STATE_HOME/machineroom/runs` elsewhere), and speaks MCP JSON-RPC 2.0 (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`) over a stdio command or an http URL. It needs no HTTP bridge. `scripts/mr-agent.mjs` has the tools `mcp_list_tools` (optional `server`) and `mcp_call_tool` (`server`, `tool`, `arguments`) beside its file, shell and web tools. A `path` or `file` argument becomes `path` in the tool use record. `scripts/acp-run.mjs` sends the enabled servers in `session/new` as `mcpServers`, `{ name, command, args, env }` for stdio and `{ name, type: 'http', url }` for http. The Claude and OpenCode parsers read `mcp__*`, `mcp_call_tool` and `mcp_list_tools` as tool `mcp`, and a `path` or `file` argument becomes a read touch.

The `acp` descriptor runs the agent through `scripts/acp-run.mjs`, which sends `initialize`, `session/new` with the enabled MCP servers in `mcpServers`, the model and effort the agent offers, and `session/prompt`, answers each permission request with its first allow option, and writes each `session/update` to the run log as one JSON object per line. A child session in `_meta` becomes its own agent. An OpenCode agent over ACP needs only a lane's `cli` block: `{"harness": "acp", "bin": "%APPDATA%\\npm\\node_modules\\@opencode\\cli\\bin\\opencode.exe", "args": ["acp"], "model": "opencode-go/deepseek-v4.1-flash"}`. No lane is added yet.

Done for the descriptor and session-reader plan: adding a harness adds one descriptor (`src/harnesses/<key>.js`, plus `server/harnesses/<key>.js` when it has a session reader), its `lanes.json` or `agents.json` entry, its entries in the remaining places listed in the table above, and its tests, without editing the pipeline, recorder or panels.
