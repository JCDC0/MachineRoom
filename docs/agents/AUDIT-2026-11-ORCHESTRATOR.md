# The orchestrator's turns, wakes and ladder: bug hunt

Date: 2026-11-03. Version 0.1.402. Read: `server/orchestrator.js`, `server/orchestrators.js`, `server/family.js`, `server/active-lanes.js`, `server/agents-config.js`, `src/model/hierarchy.js`, `docs/agents/ORCHESTRATOR-AGENT.md`, and the parts of `server/index.js`, `server/lanes-source.js` and `server/processTree.js` that call or answer those files. Nothing here repeats `AUDIT-2026-11-SUMMARY.md` or an `AUDIT-2026-11-*.md` finding.

Each row was proved with a throwaway Node script outside the repository that drove `createOrchestrator` with a fake `spawn`, or by tracing the lines named. The scripts were deleted and nothing in the tree was changed.

## The eviction test that timed out once

`tests/orchestrator.test.js` "evicts the oldest unpinned session", `Timed out waiting for turn 1 to end.` No race in `server/orchestrator.js` explains it, and I did not reproduce it.

What I checked in the code:

- `waitIdle` (`tests/orchestrator.test.js:249-256`) needs `state === 'idle'` and exactly one call line. The test allows 25 seconds for one node spawn (`:1753`).
- The turn's end is not conditional on anything the test changes. `send` reaches `startTurn`, which sets `working` (`862`), spawns (`982`), and `completeTurn` sets `idle` (`1113-1116`) with no pending message to start a second turn (the rig has no pending messages, and the state it writes at `:1746-1747` keeps `pending: []`).
- The only way to leave `working` is a thrown exception inside `completeTurn` or a write-stream callback that never runs. I ran a probe on this Node: `createWriteStream` on a missing folder fires `error` and still calls the `end` callback, so the stream path holds.
- The one real race in this area is finding 3, and the test never calls `stop()`.

The likeliest cause stays load: the test is the only one that restores 50 sessions and then calls `persist()` about four times per turn, each serialising every session, while `npm test` runs other files. That is a test allowance question, not a missed turn end. I did not rerun the file under parallel load, so this stays unproved.
